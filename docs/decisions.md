# การตัดสินใจ (Decision log)

เพิ่มข้อใหม่ไว้ท้ายไฟล์ ข้อที่ถูกล้มให้ขีดสถานะเป็น "แทนที่ด้วย #N" — อย่าลบ

---

## #1 ใช้ MCP เป็นทางที่ agent เรียก ยังไม่ทำ UTCP (2026-11-25)

**ตัดสิน:** agent สั่งอุปกรณ์ผ่าน MCP tools ของ SynaptaCode/Connect

**เหตุผล:** เจ้าของเห็นว่า UTCP ยังไม่นิ่ง ส่วน MCP ใช้งานจริงอยู่แล้วในทุก agent ที่ใช้

**ผลต่อการออกแบบ:** สเปก SDP ต้องไม่ผูกกับ MCP — descriptor ของ capability เป็น JSON Schema ล้วน
แปลงเป็น MCP tool, UTCP manual หรือ capability ของ Synapta Protocol ได้ภายหลังโดยไม่แก้ firmware

---

## #2 แยก repo: SDP = สเปก + firmware + codec, Connect = host (2026-11-25)

**สถานะ:** แทนที่ด้วย #6 — ส่วน host ย้ายมาอยู่ repo นี้ เพื่อให้ SynaptaCode ใช้ได้ด้วย

**ตัดสิน:**

| อยู่ที่ SDP (repo นี้) | อยู่ที่ Synapta Connect |
|---|---|
| สเปก wire format และ version | transport จริง (serial / TCP / BLE) |
| ไลบรารี firmware (Arduino C++, ESP-IDF, MicroPython) | device registry, จองพอร์ต |
| `sdp-core` — Rust crate แปลงข้อความล้วน ไม่มี I/O | สิทธิ์เจ้าของ, audit log |
| ตัวจำลองอุปกรณ์สำหรับเทสต์ | แฟลช / OTA, MCP tools |

**เหตุผลที่สเปกกับ firmware ต้องแยก:**
1. firmware ที่แฟลชลงบอร์ดแล้วไม่อัปเดตตาม agent (Connect ออกรุ่นวันละหลายครั้ง) — อยู่ repo เดียวกันจะเผลอแก้สองฝั่งพร้อมกันแล้วบอร์ดในสนามพัง
2. toolchain คนละชุด (PlatformIO/Arduino vs Rust ที่ต้องเข้ากับ Windows Server 2016)
3. ต้องใช้ได้โดยไม่มี Connect (ESP32 ต่อ SynaptaCode ตรง, IIoT-app, node ของ Synapta Protocol)

**เหตุผลที่ host ไม่ทำเป็น plugin แยก:** การแฟลชและสั่ง actuator เป็นสิทธิ์อันตรายที่สุด Connect มีการจับคู่ TLS,
สิทธิ์รายเครื่อง, ตัวอัปเดตที่เซ็นไว้ และ service อยู่แล้ว plugin แยกต้องสร้างทั้งหมดนี้ซ้ำ และเพิ่มจุดโจมตี

**ข้อยกเว้น:** ส่วนที่พึ่งของเสี่ยง (BLE ผ่าน WinRT, เครื่องมือแฟลชของผู้ผลิตชิป) ให้ Connect เปิดเป็น **โปรเซสลูก**
แบบเดียวกับ `helper` ที่มีอยู่ ไม่ใช่โปรดักต์แยก

## #3 รูปแบบ capability เดียวกับ Synapta Protocol (2026-11-25)

**ตัดสิน:** descriptor ของแต่ละคำสั่งใน SDP ใช้ field ชุดเดียวกับ capability ของ Synapta Protocol
(`name`, `description`, `input_schema`, `output_schema`) และตกลง version แบบ `{min, max}` เหมือนกัน

**เหตุผล:** ถ้ามีสองรูปแบบ วันหนึ่งจะขัดกันเอง และ Connect ควรประกาศ "MCU ที่เสียบอยู่" เป็น capability บนเครือข่าย
Synapta Protocol ได้โดยไม่ต้องแปลง

**ที่ SDP ต่างได้:** encoding บนสาย (ต้องเล็กพอสำหรับ MCU) และ schema ใช้ JSON Schema ชุดย่อย
(ดู [wire-format.md](wire-format.md) §Schema)

## #4 ให้ PC เป็นประตูก่อน ต่อตรงทีหลัง (2026-11-25)

**ตัดสิน:** เฟสแรก MCU ต่อผ่าน Connect บน PC เท่านั้น การให้ ESP32 ต่อ SynaptaCode ตรงเป็นเฟสหลัง

**เหตุผล:** ความปลอดภัย (จับคู่, สิทธิ์, TLS) มีอยู่แล้วบน PC; MCU ส่วนใหญ่ทำ TLS ไม่ไหว
ESP32 ทำ TLS ได้ จึงเป็นตัวแรกที่จะต่อตรงเมื่อถึงเวลา โดยใช้ข้อความ SDP ชุดเดิมบน WSS

## #5 MCP tools แบบทั่วไป ไม่สร้าง tool ต่อคำสั่ง (2026-11-25)

**ตัดสิน:** Connect เปิด `connect_device_list` / `describe` / `call` / `flash` (ชื่อจริงตัดสินตอนทำ)
agent เรียก describe ก่อนแล้วค่อย call

**เหตุผล:** MCP client มักจำรายการ tool ตอนต่อครั้งแรก เสียบบอร์ดใหม่ทีหลังแล้ว tool ที่สร้างตามอุปกรณ์จะไม่ขึ้น

## #6 ฝั่ง host เป็นไลบรารี `sdp-host` + โปรแกรม `sdp-host` ใน repo นี้ (2026-11-25)

แทนที่ #2 ในส่วนที่ว่า host อยู่ใน Connect

**ตัดสิน:**

| อยู่ที่ SDP (repo นี้) | อยู่ที่แต่ละโปรดักต์ (Connect, SynaptaCode) |
|---|---|
| สเปก, test vectors, firmware lib, `sdp-core` | สิทธิ์เจ้าของ และ audit log ของตัวเอง |
| `crates/sdp-host` — transport, registry, จองพอร์ต, แฟลช, จัดการเครื่องมือ (toolchain) | หน้า UI "อุปกรณ์" |
| โปรแกรม `sdp-host` — ไลบรารีเดียวกันห่อเป็นโปรเซสที่คุย JSON-RPC ผ่าน stdio | ช่องทาง MCP ที่รับจาก agent แล้วส่งต่อ (รายการ tool อยู่ที่ `sdp-host` — #13) |

- **Connect (Rust)** ลิงก์ crate `sdp-host` ตรง
- **SynaptaCode (Node/TypeScript)** เปิดโปรแกรม `sdp-host` เป็นโปรเซสลูก แบบเดียวกับ `pty-host` ที่มีอยู่
- ไลบรารี **ไม่ตัดสินสิทธิ์เอง** — ก่อนสั่ง capability ที่ `danger != none` หรือแฟลช จะเรียก hook `authorize(...)`
  ที่โปรดักต์ใส่มา (ผ่าน stdio คือส่งคำถามกลับไปที่โปรเซสแม่) ไม่มี hook = ปฏิเสธ

**เหตุผล:** เจ้าของต้องการให้ SDP ใช้ได้กับทุกโปรดักต์ ไม่ใช่โมดูลของ Connect และโปรดักต์ตอนนี้ใช้สองภาษา
ของยาก (DTR รีเซ็ตบอร์ด, เลข COM เปลี่ยน, ลำดับการแฟลช) จึงต้องมีที่อยู่ที่เดียว ไม่ให้แต่ละโปรดักต์เขียนเองจนพฤติกรรมไม่ตรงกัน
ถ้าวันหนึ่งทุกโปรดักต์เป็น Rust ก็แค่เลิกใช้โปรแกรม ใช้ crate ตรง ไม่ต้องแก้อะไร

**สิ่งที่ต้องรองรับ:** Connect และ SynaptaCode อาจรันบนเครื่องเดียวกันพร้อมกัน → การจองพอร์ตต้องข้ามโปรเซส
(lock file ในโฟลเดอร์กลาง บอกว่าใครถือ) ตัวที่สองต้องได้ `port_busy` พร้อมชื่อผู้ถือ ไม่ใช่เปิดชนกันจนข้อมูลปน

**ผลพลอยได้:** BLE ต้องใช้ WinRT ซึ่งลิงก์ใน exe ของ Connect ไม่ได้ (Windows Server 2016) — Connect เรียกโปรแกรม `sdp-host`
ที่ build พร้อม BLE เป็นโปรเซสลูกแทน ไม่ต้องสร้าง helper แยกอีกตัว

## #7 เครื่องมือ build/แฟลช: ใช้ของที่มีก่อน ไม่มีค่อยลง เก็บหลายเวอร์ชันในโฟลเดอร์กลาง (2026-11-25)

**ตัดสิน:**
1. **ตรวจก่อน** — หา `arduino-cli`, `esptool`, `avrdude`, board core ที่ติดตั้งอยู่แล้ว (PATH, Arduino IDE, `%LOCALAPPDATA%\Arduino15`)
   ของที่เจอใช้แบบอ่านอย่างเดียว ไม่แก้ ไม่อัปเดตทับ
2. **ไม่มีค่อยลง** — ดาวน์โหลดเวอร์ชันที่ล็อกไว้ ตรวจ hash ก่อนใช้ ลงที่โฟลเดอร์กลาง
   `%LOCALAPPDATA%\Synapta\toolchains\<เครื่องมือ>\<เวอร์ชัน>\` ทุกโปรดักต์ใช้ชุดเดียวกัน
3. **หลายเวอร์ชันอยู่คู่กันได้** — โปรเจกต์ firmware ระบุเวอร์ชันที่ต้องใช้ในไฟล์ของโปรเจกต์ (ชื่อไฟล์ตัดสินตอนทำ)
   โปรเจกต์ที่ไม่ระบุ ใช้ค่าเริ่มต้นของเครื่อง
4. **agent จัดการได้** — tool: ดูรายการที่มี (ทั้งของระบบและของโฟลเดอร์กลาง), ลงเวอร์ชันที่ต้องการ, เลือกเวอร์ชันให้โปรเจกต์, ลบ
   การลง/ลบต้องผ่าน hook `authorize` เหมือนการแฟลช (ดาวน์โหลดและรันโปรแกรมภายนอก)

**เหตุผล:** board core ต่างเวอร์ชันคอมไพล์โค้ดเดียวกันไม่ได้จริง (เช่น ESP32 core 2.x กับ 3.x เปลี่ยน API) —
ถ้ามีแค่ชุดเดียวทั้งเครื่อง อัปเดตให้โปรเจกต์หนึ่งแล้วอีกโปรเจกต์พัง การใช้ของที่ลงไว้แล้วกันการโหลดซ้ำหลายร้อย MB

## #8 ลำดับ transport: USB → WiFi → Bluetooth → SSH (2026-11-25)

**ตัดสิน:** ทำตามลำดับที่เจ้าของใช้จริง
1. **USB serial** — Uno, ESP32
2. **WiFi (TCP)** — ESP32
3. **Bluetooth** — BLE ของ ESP32 และ Bluetooth Classic (HC-05/06 ที่ขึ้นเป็น COM — ได้ฟรีจากข้อ 1)
4. **SSH** — อุปกรณ์เครือข่าย (router, switch, บอร์ด Linux) ที่มี OS อยู่แล้ว ไม่ได้พูด SDP

RS485 / Modbus เลื่อนไปหลังจากนี้ (ยังไม่มีงานที่ใช้)

**ผลต่อการออกแบบ:** transport ใน `sdp-host` เป็น trait เดียว (เปิด/ปิด/อ่าน/เขียน + ค้นหาอุปกรณ์) เพิ่มชนิดใหม่โดยไม่แตะส่วนอื่น
SSH ไม่ใช่ท่อ byte ของ SDP แต่เป็นอุปกรณ์แบบ "ดิบ" — agent สั่งคำสั่งแล้วได้ข้อความกลับ ไม่มี describe (ดู transports.md §SSH)

## #9 เข้ารหัสลิงก์ไร้สาย PC ↔ อุปกรณ์ เผื่อการดักจับ (2026-11-25)

**ตัดสิน:** การยืนยันตัวตนระหว่าง agent กับ PC เป็นหน้าที่ของ SynaptaCode/Connect อยู่แล้ว (ไม่มีคนนอกใช้)
แต่ช่วง PC ↔ อุปกรณ์บน WiFi/BLE วิ่งผ่านอากาศ จึงเข้ารหัสไว้กันการดักอ่านและส่งคำสั่งปลอม:
- กุญแจ (PSK) ได้ตอนเสียบ USB ครั้งแรก — จับคู่จากระยะไกลไม่ได้
- ESP32 ใช้ AES-CCM (มี hardware) เปิดเป็นค่าเริ่มต้น
- Uno ที่ต่อผ่านโมดูลไร้สายเข้ารหัสไม่ไหว → ติดป้าย `link_secure = false` และคำสั่ง `actuator`/แฟลชปิดเป็นค่าเริ่มต้น
- USB ไม่เข้ารหัส (สายต่อตรงกับเครื่อง)

**เหตุผล:** เจ้าของเห็นว่าไม่เร่ง แต่ทำเผื่อไว้ได้ — ถ้าไม่วางที่ไว้ในสเปกตอนนี้ การเพิ่มทีหลังจะเปลี่ยนรูปเฟรมและทำให้บอร์ดที่แฟลชไปแล้วคุยไม่ได้
ทำจริงพร้อมเฟส WiFi

## #10 Body เป็น CBOR แบบ array + key เลข (2026-11-25)

**ตัดสิน:** ทุกข้อความเป็น `[t, id, m]` โดย `m` เป็น map ที่ key เป็นเลข ผู้ส่งเข้ารหัสแบบ deterministic ผู้รับข้าม key ที่ไม่รู้จัก
(รายละเอียดใน wire-format.md)

**เหตุผล:** Uno มี RAM 2 KB และเฟรม 128 ไบต์ JSON ใหญ่และ parse กิน RAM ส่วน key แบบข้อความกินที่ทุกเฟรม
การอ่านด้วยตาไม่ได้แก้ที่เครื่องมือฝั่ง PC (`sdp-sim`, ตัวถอดใน `sdp-host`) การเข้ารหัสแบบ deterministic ทำให้ test vectors เทียบ byte ได้
การข้าม key ที่ไม่รู้จักทำให้เพิ่ม field ได้โดยไม่ต้องขึ้น version

## #11 Schema: JSON Schema ชุดย่อย ลึกไม่เกิน 3 ชั้น host ตรวจเต็ม firmware ตรวจชนิดและช่วง (2026-11-25)

**ตัดสิน:** ดูรายการคำและข้อจำกัดใน wire-format.md §Schema — schema ใช้ key ข้อความตาม JSON Schema แปลงเป็น JSON ได้ตรง

**เหตุผล:** host ตรวจเต็มเพื่อให้ agent ได้ error ที่อ่านรู้เรื่อง firmware ตรวจแค่ชนิดและช่วงเป็นด่านสุดท้ายกันของจริงพัง
จำกัดความลึกเพราะ parser recursive บน AVR ลึกไม่จำกัด = stack ล้น

## #12 การเข้ารหัสลิงก์ไร้สาย: PSK จาก USB + AES-128-CCM + counter (2026-11-25)

**ตัดสิน:** ดู wire-format.md §การเข้ารหัส — session key ใหม่ทุกครั้งจาก nonce สองฝั่ง, counter กันเล่นซ้ำ,
host ที่มีกุญแจแล้วปฏิเสธการถอยไปไม่เข้ารหัส, `pair` ทำได้ผ่าน USB เท่านั้น

**เหตุผล:** ทำตาม #9 โดยไม่ต้องมี TLS (MCU ส่วนใหญ่ทำไม่ไหว) ESP32 มี AES และ SHA ใน hardware
ที่ว่างใน `flags` วางไว้ตั้งแต่ v1 จึงเปิดใช้ทีหลังได้โดยไม่ต้องแฟลชบอร์ดเดิมใหม่ — bit 1 ของ `flags` ใช้เป็นที่อยู่ RS485 ไปด้วย
(ปิดคำถาม **[เปิด]** เรื่อง address ใน transports.md)

## #13 รายการ tool ของ agent อยู่ใน `sdp-host` โปรดักต์แค่ส่งต่อ (2026-11-25)

แทนที่ส่วน "MCP tools ที่เปิดให้ agent อยู่ที่โปรดักต์" ของ #6

**ตัดสิน:**
- `sdp-host` มี `tools()` คืนรายการ tool (ชื่อ, คำอธิบาย, input schema) และ `call_tool(ชื่อ, input)` ที่ทำงานจริง
  — ทั้งใน crate และเป็นเมธอด JSON-RPC ของโปรแกรม `sdp-host`
- โปรดักต์รับ MCP จาก agent แล้วส่งต่อสองเมธอดนี้ ตอบ `authorize` และเก็บ audit log — ไม่เขียนคำอธิบายหรือ schema ของ tool เอง
  เติมคำนำหน้าชื่อได้ (เช่น `connect_`) ถ้าชนกับ tool อื่นของโปรดักต์
- ความสามารถของบอร์ดไม่กลายเป็น tool แยก ยังใช้ `device_describe` + `device_call` ตาม #5
- `sdp-host` ไม่เป็น MCP server เองในตอนนี้ (ถ้าทำ agent จะข้ามสิทธิ์และ audit log ของโปรดักต์)
  ภายหลังถ้าต้องใช้กับ agent ตรงโดยไม่มีโปรดักต์ ค่อยเพิ่มโหมด `--mcp` ที่อ่านสิทธิ์จากไฟล์ตั้งค่า

**เหตุผล:** ถ้าสองโปรดักต์เขียน tool เอง คำอธิบายและ schema จะค่อย ๆ ไม่ตรงกัน agent ใช้งานต่างกันในแต่ละแอป
tool มีที่อยู่ที่เดียว เพิ่ม tool ใน `sdp-host` แล้วทุกโปรดักต์ได้ทันที

## #14 ไลบรารี Arduino: schema เขียนเป็น JSON, ตรวจตอน begin(), บังคับ onLinkLost ตอนสั่งงาน (2026-11-25)

**ตัดสิน:**
- ผู้เขียน firmware เขียน schema เป็นข้อความ JSON ใน flash (`SDP_CAPABILITY(..., R"({...})", ...)`)
  ไลบรารีแปลงเป็น CBOR ระหว่างส่ง describe และเรียง key ตามกฎ encoding ให้เอง โดยไม่พักใน RAM
  — แทนที่ข้อความเดิมใน wire-format.md ที่ว่า firmware เก็บ byte CBOR ที่เข้ารหัสเสร็จแล้ว
- schema ผิด (JSON เสีย, คำที่สเปกไม่รองรับ, ลึกเกิน 3 ชั้น, descriptor ใหญ่เกินหนึ่งหน้า) ตรวจตอน `begin()`
  พิมพ์เหตุผลทาง serial และตอบทุกคำขอด้วย `error 5` — แทน "แจ้งตอน build" ที่ทำไม่ได้ใน Arduino IDE
- capability ระดับ `actuator`/`destructive` ถูกปฏิเสธ (`error 5`) ถ้า firmware ไม่ได้ตั้ง `onLinkLost()`
  และ `begin()` พิมพ์คำเตือน (ปิดคำถาม **[เปิด]** ใน safety.md)
- firmware ที่ไม่มีลิงก์ไร้สายตอบ `pair`/`unpair` ด้วย `error 5` — การจับคู่มาพร้อมเฟส 2
- `on_link_lost` นับจากเฟรมใดก็ได้ที่มาจาก host ไม่ใช่เฉพาะ `ping` — describe ยาว ๆ ไม่ควรทำให้ link หลุด

**เหตุผล:** ผู้ใช้ Arduino (และ agent ที่เขียน firmware ให้) เขียน JSON Schema ได้ทันที ไม่ต้องมีเครื่องมือแปลงก่อนคอมไพล์
ซึ่ง Arduino IDE ไม่มีขั้นตอนให้รัน การบังคับ onLinkLost ตอนคอมไพล์ทำไม่ได้เพราะตาราง capability กับ `onLinkLost()` อยู่คนละที่
ใน sketch จึงปฏิเสธตอนสั่งงานแทน — ผู้เขียนเห็นทันทีครั้งแรกที่ลอง ไม่ใช่ตอนปั๊มค้าง

**ราคาที่จ่าย:** บน Uno ไลบรารี + LedDemo ใช้ flash ราว 24 KB จาก 32 KB (ตัวแปลง JSON และตัวตรวจ schema ราว 6 KB)
ถ้าโปรเจกต์ Uno จริงพื้นที่ไม่พอ ทางออกคือเครื่องมือแปลง schema เป็น byte CBOR ล่วงหน้าแล้วตัดตัวแปลงออก

## #15 ควบคุมเครื่องที่มี OS แบบชั่วคราวไม่ต้องติดตั้ง = โหมดพกพาของ Synapta Connect ไม่ใช่ส่วนของ SDP (2026-11-25)

**ตัดสิน:**
- งานนี้คือการรัน exe เดียวโดยไม่ต้องติดตั้ง แล้วให้ Connect/SynaptaCode มองเห็นและควบคุมได้: ดูจอ, เมาส์, คีย์บอร์ด, คุมเฉพาะแอปเดียว
  ทำเป็น **Synapta Connect Portable** ใน repo ของ Connect
- ขอบเขตแรก: LAN / Tailscale (ไม่มี relay ข้ามอินเทอร์เน็ต) และ Windows ก่อน
  แต่แยกส่วนที่ขึ้นกับ OS (จับจอ, input, รายการหน้าต่าง) ไว้หลัง interface เดียว เพิ่ม macOS/Linux ได้โดยไม่ต้อง refactor
- SDP ยังเป็นโปรโตคอลของอุปกรณ์ที่ไม่มี OS ตามเดิม

**เหตุผล:** Connect มีการดูจอ, input, การจับคู่ด้วย OTP (SPAKE2) + mTLS และ tool `connect_*` ใน SynaptaCode อยู่แล้ว
ถ้าทำใน SDP ต้องรื้อสเปก (ขาอุปกรณ์ → host จำกัด 4096 ไบต์ ส่งภาพหน้าจอไม่ได้, ไม่มี stream สำหรับ terminal),
ต้องทำการจับคู่ผ่านเครือข่ายใหม่ (ของ SDP ต้องเสียบ USB) และจะมีโค้ดควบคุมจอสองชุดที่แก้ช่องโหว่ไม่พร้อมกัน
