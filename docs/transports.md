# Transport และกับดัก

ทุกข้อในหัวข้อ "กับดัก" คือสิ่งที่จะพังจริงถ้าไม่ออกแบบรองรับตั้งแต่แรก

ลำดับที่ทำ (decisions #8): **USB → WiFi → Bluetooth → SSH** แล้วค่อย RS485/Modbus
ทุกชนิดอยู่ใน `sdp-host` และใช้ trait เดียวกัน (เปิด / ปิด / อ่าน / เขียน + ค้นหาอุปกรณ์)

## Serial — USB-CDC, USB-UART, RS232

- Rust crate: `serialport` (ไม่พึ่ง API ใหม่กว่า Windows Server 2016)
- ค่าเริ่มต้น 115200 8N1 อุปกรณ์ที่ต่างจากนี้ เจ้าของตั้งใน panel

**กับดัก**
1. **เปิดพอร์ตแล้วบอร์ดรีเซ็ต** — Arduino ส่วนใหญ่ต่อ DTR เข้าขา reset เปิดพอร์ตทุกครั้ง = รีเซ็ตทุกครั้ง
   ถ้า agent อ่านค่าเซ็นเซอร์ทุก 5 วินาทีแบบเปิด-ปิด เครื่องจักรจะรีเซ็ตทุก 5 วินาที
   → เปิดค้างไว้ (registry ถือพอร์ต) และให้ตั้งได้ว่าจะยก DTR/RTS หรือไม่ หลังเปิดรอ `hello_ack` ไม่เกิน ~2 วินาที (bootloader)
2. **เลข COM เปลี่ยน** — บอร์ด USB ในตัว (Leonardo, ESP32-S2/S3, RP2040) ได้พอร์ตใหม่ตอนเข้า bootloader
   → ระบุตัวด้วย VID/PID/serial ไม่ใช่ชื่อพอร์ต (ดู architecture.md §ตัวตน)
3. **เขียนพร้อมกันสองทาง** — agent สองตัว (หรือ agent กับ Arduino IDE ของเจ้าของ) เปิดพอร์ตเดียวกัน ข้อมูลปนจนอ่านไม่ออก
   → registry จองพอร์ตทีละเจ้าของ คืนพอร์ตเมื่อหมดเวลาไม่ใช้ และมีคำสั่ง "ปล่อยพอร์ต" ให้เจ้าของเอาไปใช้ IDE ได้
4. **บอร์ดพิมพ์ log ปนกับ SDP** — firmware เดิมมักมี `Serial.println` → framing COBS ทิ้ง byte ที่ไม่อยู่ในเฟรมได้
   และ Connect เก็บ byte นอกเฟรมเป็น "console log" ให้ agent อ่านได้ (มีประโยชน์ตอน debug)

## RS485 / Modbus

- RS485 เป็น half-duplex หลายอุปกรณ์บนสายเดียว: SDP บน RS485 ต้องมีที่อยู่ (address 1 ไบต์) นำหน้าเฟรม — ใช้ `flags` bit 1 (wire-format.md)
- อุปกรณ์อุตสาหกรรมเดิมพูด Modbus RTU อยู่แล้ว → รองรับเป็น "codec ดิบ" ใน Connect (`tokio-modbus`) ไม่ต้องแปลงเป็น SDP

## WiFi (TCP)

- ค้นหา: อุปกรณ์ประกาศ mDNS `_sdp._tcp` (Connect ใช้ `mdns-sd` อยู่แล้ว) พร้อม `device_id` ใน TXT
- เข้ารหัสด้วย PSK ที่ได้ตอนจับคู่ผ่าน USB ครั้งแรก + AES-CCM (ESP32 มี hardware) เปิดเป็นค่าเริ่มต้น (decisions #9)
  กันคนในวง WiFi เดียวกันดักอ่านหรือส่งคำสั่งปลอม
- กับดัก: ESP32 หลุด WiFi แล้วต่อใหม่ได้ IP ใหม่ → ผูกด้วย `device_id` ไม่ใช่ IP

## Bluetooth LE

- Rust crate: `btleplug` ใช้ WinRT ซึ่ง **มี API ใหม่กว่า Windows Server 2016** → ลิงก์ตรงใน exe หลักไม่ได้ (exe จะเปิดไม่ขึ้นบน 1607)
  → Connect เรียกโปรแกรม `sdp-host` (build พร้อม BLE) เป็นโปรเซสลูก บนเครื่องที่ไม่รองรับ โปรเซสลูกเปิดไม่ขึ้นแต่ Connect ยังทำงานได้ (decisions #6)
- เข้ารหัสแบบเดียวกับ WiFi (decisions #9) — การจับคู่ BLE ของระบบเองไม่พอ เพราะหลายบอร์ดใช้แบบ "Just Works" ที่ถูกดักได้
- GATT service ของ SDP: characteristic เดียวแบบ write + notify, UUID กำหนดใน spec **[เปิด]**
- BLE Classic (SPP) ของ HC-05/HC-06 จะขึ้นเป็น COM บน Windows หลังจับคู่ → ใช้ทาง serial ได้เลย

## SSH — อุปกรณ์เครือข่าย

สำหรับ router, switch, บอร์ด Linux (Raspberry Pi, OpenWrt) ที่มี OS และ SSH อยู่แล้ว — **ไม่พูด SDP**
เป็นอุปกรณ์แบบ "ดิบ": agent ส่งคำสั่ง ได้ stdout/stderr + exit code กลับ ไม่มี describe

- Rust crate: `russh` (เขียนด้วย Rust ล้วน ไม่พึ่ง OpenSSH ของเครื่อง) — ต้องเช็ก `dumpbin /imports` ตอนทำ
- รหัสผ่าน/กุญแจเก็บที่โปรดักต์ ไม่ใช่ที่ `sdp-host` — ส่งเข้ามาตอนเปิด session เท่านั้น

**กับดัก**
1. **host key** — ครั้งแรกจำ fingerprint ไว้ (ให้เจ้าของยืนยัน) ครั้งถัดไปถ้าเปลี่ยน ต้องปฏิเสธและแจ้ง
   ไม่งั้นใครปลอมเป็น router ก็รับรหัสผ่านไปได้
2. **อุปกรณ์เครือข่ายหลายรุ่นไม่มี exec** (Cisco IOS, MikroTik บางรุ่น) — ต้องเปิด shell แบบ interactive แล้วรอ prompt
   → รองรับทั้งสองโหมด ตั้ง regex ของ prompt ได้ต่ออุปกรณ์
3. **คำสั่งที่ตัดเน็ตตัวเอง** (เปลี่ยน IP, ปิด interface) — session หลุดกลางคำสั่ง ต้องรายงานว่า "ไม่รู้ผล" ไม่ใช่ "ล้มเหลว"
   คำสั่ง SSH ทุกคำสั่งถือเป็น `danger = destructive` เป็นค่าเริ่มต้น เจ้าของลดระดับรายอุปกรณ์ได้
